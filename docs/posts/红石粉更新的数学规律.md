红石线更新顺序的判断

# 前言

我们知道红石粉的更新具有空间随机性。因此玩家们倾向于认为一连串红石粉组成的线的更新顺序，是否有位置性，是无法预测，也不值得耗费精力去预测的。

但事实上，红石粉的变动、更新顺序，是有固定的数学规律的。

# 数学规律

粉的更新顺序中存在一些数学规律。这些规律可以用来操作红石线的激活顺序。这些规律地发现需要归功于 EarthComputer 等早期开始对红石线进行研究的玩家。

为了了解这些规律，我们必须从HashSet的结构看起。

红石粉的更新使用了HashSet。HashSet是一种哈希表，是一种通过键（Key）直接访问对应值（Value）的高效数据结构。其中的存储流程大致如下：
```
Object(物品)
  │
  │ hashCode() 计算 哈希值
  ↓
hash（哈希值）
  │
  │ 某种转换+扰动
  ↓
bucket index（哈希桶号）
  │
  ↓
HashTable[bucket index]（哈希表）
  │
  ├── 物品A
  ├── 物品B
  └── …
```

（想象一组固定数量的抽屉，`桶号（bucket index）`就是抽屉的编号。
每个存入的物品都会根据自己的某种`特征（hashCode）`，通过一个计算规则决定应该放进哪个抽屉。）

如果多个物品被分配到了同一个抽屉，那么先加入的排前，后加入的靠后。同时这会产生产生「哈希冲突」，增加寻找某个特定物品的耗时，这也是为什么我们希望物品的` hashCode()` 结果尽可能分散。

`HashSet`的默认有**16个“抽屉”**，虽然当存储的对象过多时会扩充，但红石粉的更新源恒定只有7个，永不会扩充。
因此能够呈现出一定的规律。

哈希值的计算由游戏决定：
```Java
hashCode = x + 31 * (y + 31 * z)
```
通过哈希值计算坐标在数组中存储序号的公式由Java决定：
```java
hash = hashCode ^ (hashCode >>> 16);
bucketIndex = (length - 1) & hash
```
这些计算方式带来了首批规律。

## 规律1 ：

 > 虽然有默认16个“抽屉”但 大约97%的情况下，七个更新核往往仅落在其中三个中。其中，原点O独自成落入一个抽屉，-Y、+Z、+X落入同一个抽屉，而+Y、-Z、-X落入同一个抽屉。

为何会这样呢？

一个粉的7个更新核，分别是 粉位置，与粉周围六个毗邻位置。
其中，相对于粉自身的位置，它们仅在x，y，z轴增减1格。

回顾哈希值算式：
`hashCode = x + 31 * (y + 31 * z) 	= x + 31y + 961z`

这意味着：
当x轴±1时，哈希值仅± 1；
当y轴±1时，哈希值± 31；
当z轴±1时，哈希值± 961 。

实际上，7个更新核的哈希值是相当接近的。
再观哈希桶号的算式前半：
`hash = hashCode ^ (hashCode >>> 16);`

这里的运算的意思是：将哈希值的高16位取出，并于哈希值做异或运算。

而一个32位整数的低16位可以表示：
`2^16−1=65535`
也就是说，低16位能够容纳65536种不同的数，而这7个更新核之间的差距最大才1922。

因此，只要没有刚好跨过低16位的边界，这7个更新核的 高16位就完全不会发生变化。

换句话说，在绝大多数情况下，这7个更新核的 hashCode 都可以看成：相同的高16位 | 不同的低16位
而` hashCode >>> 16 `恰好就是把这个相同的高16位取出来。

因此，7个更新核本质上都是在用同一个高16位去和自己的低16位进行异或。
此时，真正能够造成差异的，就只剩下 hashCode 的低16位。

然后是后半段：
`bucketIndex = (length - 1) & hash`

由于默认16个抽屉，length是16。

所以实际上是
`bucketIndex = 15 & hash`

而`15 = 0000 0000 0000 1111`，这意味着，桶号实际上只取最终 hash 的最低4位。hash的这最低4位的根基，是hashCode的最低4位。因此我们真正需要关注的，还是hashCode自己的最低4位。

而 hashCode 是由` x + 31y + 961z `得到的。因为**31除以16的余数和-1相同，961除以16的余数和1相同**，所以这个 hashCode 的最低4位，实际上只与` x - y + z `有关。

设中心点`x - y + z`的结果为A：
```
+X： A + 1
-X： A - 1

+Y： A - 1
-Y： A + 1

+Z： A + 1
-Z： A - 1
```
致此可以证出3个分组：

> 原点O独自成落入一个抽屉，-Y、+Z、+X落入同一个抽屉，而+Y、-Z、-X落入同一个抽屉

那97%的概率又是哪来的呢？

我们先前提到过，7个核高16位相同的前提是：没有刚好跨过低16位的边界。

65535个数字中，多少数字跨越了这个边界呢？既然最极端差距是之前提到的1922，可以确定**65535个数字中有1922个数**增减时会跨过边界。其出现的概率是`1922/65536 ≈3 %`。 那么剩下的，“安全”的，出现“`原点O独自成落入一个抽屉，-Y、+Z、+X落入同一个抽屉，而+Y、-Z、-X落入同一个抽屉`”的情况的概率就是97%了。

而剩下不满足这个规律的，红石粉的位置称为“失效点”。至此，是红石粉相关的，第一个数学上的规律。

## 规律2:

> 失效点有固定的，可预测的区间和踪迹。如果点 A 是失效点，那么与点 A 的 `hashCode `相差至少 1922 的点 B，就不可能与 A 处于同一个“失效范围”中

但这还没有结束。哪些点（失效点）会不满足刚刚得出的结论呢？

结合先前得出的结论：
- X 每移动一格，hashCode 只变化 1；Y 每移动一格变化 31；Z 每移动一格变化 961。
- 低16位的边界每隔65536出现一次。
- 导致规律失效的原因，是 hashCode 的低16位在增减 961 时跨过了 65536 的边界。

因此，只要 hashCode 处在距离这个边界足够近的范围内，就可能成为失效点。

例如，考虑hashCode最远的两个更新核（+-Z），它们的 hashCode 相差1922。因此，如果一个红石粉的 hashCode 距离低16位边界不到1922，那么它周围的更新核就有可能跨过这个边界，进而导致我们前面“7个核高16位相同”的结论失效。

现在就能看出三个方向的“失效范围”了。


> 沿 X 轴：
每移动一格，hashCode 只变化1。
因此，一个宽度约1922的失效区域在 X 方向上持续。一旦进入这个区域，沿 X 方向连续移动上千格，都可能仍然处于失效区之中。

> 沿 Y 轴：
每移动一格变化31，所以同样的失效区大约只能持续：1922 ÷ 31 ≈ 62格。

> 沿 Z 轴：
每移动一格变化961，因此危险区域大约只能持续：1922 ÷ 961 ≈ 2
格。

由此还能得出：

> 如果点 A 是失效点，那么与点 A 的 hashCode 相差至少 1922 的点 B，就不可能与 A 一样处于“失效范围”中。
