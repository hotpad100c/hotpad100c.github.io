红石线更新顺序的判断

# 前言

我们知道红石粉的更新具有空间随机性。因此玩家们倾向于认为一连串红石粉组成的线的更新顺序，是否有位置性，是无法预测，也不值得耗费精力去预测的。

但事实上，红石粉的变动、更新顺序，是有固定的数学规律的。

# 数学规律

粉的更新顺序中存在一些数学规律。这些规律可以用来操作红石线的激活顺序。这些规律地发现需要归功于 EarthComputer 等早期开始对红石线进行研究的玩家。

为了了解这些规律，我们必须从HashSet的结构看起。

红石粉的更新使用了`HashSet`。`HashSet`是一种哈希表，是一种通过键（Key）直接访问对应值（Value）的高效数据结构。其中的存储流程大致如下：
```
Object(物品)
  │
  │ hashCode() 计算 哈希值
  ↓
hash（哈希值）
  │
  │ 某种转换+扰动
  ↓
bucket index（哈希桶号）
  │
  ↓
HashTable[bucket index]（哈希表）
  │
  ├── 物品A
  ├── 物品B
  └── …
```

（想象一组固定数量的抽屉，`桶号（bucket index）`就是抽屉的编号。
每个存入的物品都会根据自己的某种`特征（hashCode）`，通过一个计算规则决定应该放进哪个抽屉。）

> 如果多个物品被分配到了同一个抽屉，那么先加入的排前，后加入的靠后。

同时这会产生产生「哈希冲突」，增加寻找某个特定物品的耗时，这也是为什么我们希望物品的` hashCode()` 结果尽可能分散。

`HashSet`的默认有**16个“抽屉”**，遍历时序号从低到高遍历。当存储的对象过多时会扩充抽屉数量，但红石粉的更新核恒定只有7个，所以不会触发扩充。

此外，7个更新核以 `O -Y +Y -Z +Z -X +X`的顺序依次加入这个`HashSet`。当被分配置同一个抽屉时，同抽屉内的更新核按照这个加入顺序被激发。

哈希值的计算由游戏决定：
```Java
hashCode = x + 31 * (y + 31 * z)
```
通过哈希值计算序号的公式由Java决定：
```java
hash = hashCode ^ (hashCode >>> 16);
bucketIndex = (length - 1) & hash
```
这些特性共同带来了一些规律。

## 规律1 ：

 > 虽然有默认16个“抽屉”但 大约97%的情况下，七个更新核往往仅落在其中三个中。其中，原点O独自成落入一个抽屉，-Y、+Z、+X落入同一个抽屉，而+Y、-Z、-X落入同一个抽屉。

为何会这样呢？

一个粉的7个更新核，分别是 粉位置，与粉周围六个毗邻位置。
其中，相对于粉自身的位置，它们仅在x，y，z轴增减1格。

回顾哈希值算式：
`hashCode = x + 31 * (y + 31 * z) 	= x + 31y + 961z`

这意味着：
当x轴±1时，哈希值仅± 1；
当y轴±1时，哈希值± 31；
当z轴±1时，哈希值± 961 。

实际上，7个更新核的哈希值是相当接近的。
再观哈希桶号的算式前半：
`hash = hashCode ^ (hashCode >>> 16);`

这里的运算的意思是：将哈希值的高16位取出，并于哈希值做异或运算。

而一个32位整数的低16位可以表示：
`2^16−1=65535`
也就是说，低16位能够容纳65536种不同的数，而这7个更新核之间的差距最大才1922。

因此，只要没有刚好跨过低16位的边界，这7个更新核的 高16位就完全不会发生变化。

换句话说，在绝大多数情况下，这7个更新核的 hashCode 都可以看成：相同的高16位 | 不同的低16位
而` hashCode >>> 16 `恰好就是把这个相同的高16位取出来。

因此，7个更新核本质上都是在用同一个高16位去和自己的低16位进行异或。
此时，真正能够造成差异的，就只剩下 hashCode 的低16位。

然后是后半段：
`bucketIndex = (length - 1) & hash`

由于默认16个抽屉，length是16。

所以实际上是
`bucketIndex = 15 & hash`

而`15 = 0000 0000 0000 1111`，这意味着，桶号实际上只取最终 hash 的最低4位。hash的这最低4位的根基，是hashCode的最低4位。因此我们真正需要关注的，还是hashCode自己的最低4位。

而 hashCode 是由` x + 31y + 961z `得到的。因为**31除以16的余数和-1相同，961除以16的余数和1相同**，所以这个 hashCode 的最低4位，实际上只与` x - y + z `有关。

设中心点`x - y + z`的结果为A：
```
+X： A + 1
-X： A - 1

+Y： A - 1
-Y： A + 1

+Z： A + 1
-Z： A - 1
```
致此可以证出3个分组：

> `原点O`独自成落入一个抽屉，`-Y、+Z、+X`落入同一个抽屉，而`+Y、-Z、-X`落入同一个抽屉。这三个分组里，按照前文列出的顺序（同样也是7个更新g核加入HashSet时的顺序）依次激发更新核。但3个组谁先谁后仍有`3x2x1=6`种组合。

那97%的概率又是哪来的呢？

我们先前提到过，7个核高16位相同的前提是：没有刚好跨过低16位的边界。

65535个数字中，多少数字跨越了这个边界呢？既然最极端差距是之前提到的1922，可以确定**65535个数字中有1922个数**增减时会跨过边界。其出现的概率是`1922/65536 ≈3 %`。 那么剩下的，“安全”的，出现“`原点O独自成落入一个抽屉，-Y、+Z、+X落入同一个抽屉，而+Y、-Z、-X落入同一个抽屉`”的情况的概率就是97%了。

- 图中黑线右侧，彩色的色块代表该位置符合97%规律，灰色色块代表其不符合。
- 绿色标记①和③为规则生效区，可以看到明显有规律的色块排列。

## 规律2:

> 失效点有固定的，可预测的区间和踪迹。如果点 A 是失效点，那么与点 A 的 `hashCode `相差至少 1922 的点 B，就不可能与 A 处于同一个“失效范围”中

但这还没有结束。哪些点（失效点）会不满足刚刚得出的结论呢？

结合先前得出的结论：
- X 每移动一格，hashCode 只变化 1；Y 每移动一格变化 31；Z 每移动一格变化 961。
- 低16位的边界每隔65536出现一次。
- 导致规律失效的原因，是 hashCode 的低16位在增减 961 时跨过了 65536 的边界。

因此，只要 hashCode 处在距离这个边界足够近的范围内，就可能成为失效点。

例如，考虑hashCode最远的两个更新核（+-Z），它们的 hashCode 相差1922。因此，如果一个红石粉的 hashCode 距离低16位边界不到1922，那么它周围的更新核就有可能跨过这个边界，进而导致我们前面“7个核高16位相同”的结论失效。

现在就能看出三个方向的“失效范围”了。

(下图中为失效区分布的可视化。灰色为失效区；白色线描述了坐标轴；绿色框为一个失效区的“段落”。失效区群由一个个段落排列而成。）

> 沿 X 轴：
每移动一格，hashCode 只变化1。
因此，一个宽度约1922的失效区域在 X 方向上持续。一旦进入这个区域，沿 X 方向连续移动上千格，都可能仍然处于失效区之中。

## 规律3:

> 97%规则生效时，3个分组有`6`种组合。`-Y+X+Z`定为`G+`，`中心点`为`自身`，`+Y-X-Z`为`G-`。其中，`自身`一组在顺序中间的概率为`50%`。

| 顺序 | 占比 |
| --- | --- |
| `G+ → 自身 → G-` | **25%** |
| `G- → 自身 → G+` | **25%** |
| `自身 → G+ → G-` |12.5% |
| `自身 → G- → G+` |12.5% |
| `G+ → G- → 自身` |12.5% |
| `G- → G+ → 自身` |12.5% |

在前文中，我们提到：
> 而`15 = 0000 0000 0000 1111`，这意味着，桶号实际上只取最终 `hash `的最低4位。`hash`的这最低4位的根基，是`hashCode`的最低4位。因此我们真正需要关注的，还是`hashCode`自己的最低4位。

而 `hashCode` 是由`x + 31y + 961z`得到的。因为31除以16的余数和-1相同，961除以16的余数和1相同，==所以这个 hashCode 的最低4位，实际上只与`x - y + z`有关。==.{important}

我们继续将` x - y + z `的结果记A。而在97%的情况下，
因为次数影响`hashCode`的低4位，
因此此数与` hashCode `的高16位中的 前4位（此时它们为同一数字，看作`B`）按位异或的结果决定了`原算式`的最后4位，
进而决定了最终的 桶号 。

如果两个组的 x - y + z 仅在最低位（bit0）不同，则它们的 桶号 也一定相邻，则它们的排序也相邻。
另外落单的一组因为bit0外的其它位也不同而排到其它地方。

我们假设 `u = A^B`（自身）、`v = (A+1)^B`（G+组）、`w = (A−1)^B`（G-组）。（此处`^`为`XOR`）

- 当`A` 为**偶数**时，`A` 与 `A+1` 只在 bit0 不同，
  - 因此 `u` 与 `v` 只在 bit0 不同
  - 因此 `u` 与 `v`得到的桶号将是相邻整数
  - 因此 **没有第三个值能插在它们中间**
  - 因此`w` 不可能在中间。
  
- 当`A` 为**奇数**时，`A` 与 `A−1` 只在 bit0 不同
  - 同上，因此 `u` 与 `w` 的桶号相邻
  - 因此 `v` 不可能插在中间。

每组出现在中间的可能性可以列为如下：
```
                    A
                 /     \
              偶数       奇数
              50%        50%
             /   \       /   \
          自身   G+    自身   G-
          50%   50%    50%   50%
```

如图，在中间的只可能是「自身」或「与 `A` 同奇偶的那一组」，两者各占一半
既：
- 自身中间 50%，
- `G+` 在中间 25%（只在 `A` 偶数时）
- `G-` 在中间 25%（只在 `A` 奇数时）。

三种情况各自再按排列组合，可得到25%，25%，12.5%，12.5%，12.5%，12.5%的结论。

## 规律4 
> 尽管7个更新核有 7! 种组合，但实际只有60种能够出现。

先前，我们一直将目光放在“生效区”，也就是97%的规则生效的区域。
现在让我们思考一下失效区内的分布。

若一个位置想处于失效区，

则它的 **hashCode 低 16 位** （后称`L`，指“Low”）加减 961 或 31或 1 时，

需要超过 16位 可表示的边界，即高于 65536。或者低于 0 。

这样一来，它的某几个更新核的低16位将“越界”，改变自己 hashCode 的高16位，进而导致这些更新核被分到别的 bucketIndex，导致规律失效。

因此可以推出每个方向的进位/借位条件。

**正向方向**（向上进位）：

| 方向 | 计算 | 进位条件 |
|-----|------|---------|
| `+Z` | `L + 961` | 当 `L ≥ 64575` |
| `+Y` | `L + 31` | 当 `L ≥ 65505` |
| `+X` | `L + 1` | 当 `L = 65535` |

**负向方向**（向下借位）：

| 方向 | 计算 | 借位条件 |
|-----|------|---------|
| `-Z` | `L - 961` | 当 `L ≤ 960` |
| `-Y` | `L - 31` | 当 `L ≤ 30` |
| `-X` | `L - 1` | 当 `L = 0` |

现在将**正向的阈值从小到大排列**：
```
64575 < 65505 < 65535
  ↑        ↑        ↑
 +Z       +Y       +X
```
**负向的阈值从大到小排列**：
```
960 > 30 > 0
 ↑     ↑    ↑
-Z    -Y   -X
```
观察阈值的大小关系可以发现：

* 如果L要在X轴增减时超出，则此时Y和Z轴一定也会超出（如果因X坐标增减1都会导致超出，那Y的31和Z的961肯定也会超出）；
* 如果L要在Y轴增减时超出，则此时Z轴一定也会超出，但X不一定超出；
* 如果L要在Z轴增减时超出，X和Y均不一定超出。

除此以外还有相当显而易见的一点：

- 当 L ≥ 64575 时，只可能向上进位（L 太大，不可能在减少时 ≤ 960）
- 当 L ≤ 960 时，只可能向下借位（L 太小，不可能在增加时 ≥ 64575）

这几点一结合，排除了相当多的组合。现在唯一剩下的，失效区 里能出现的情况如下列出：

* `{+Z}` 进位
* `{+Z,+Y}` 进位
* `{+Z,+Y,+X}` 进位
* `{-Z}` 进位
* `{-Z,-Y}` 进位
* `{-Z,-Y,-X}` 进位

那现在就可以考究这6种失效情况各能制造多少组合了。

让我们回到 规律3 时的做法：

> 我们继续将由` x - y + z `影响的，`hashCode`的低4位记作A，` hashCode `的高16位中的 前4位 记作B。

在生效区时，
```
自身： A ^ B
G+组：(A+1) ^ B 
G-组：(A-1) ^ B
```
但在失效区内情况不同：G+或者G-组里，某几个更新核的 B 会 `+1（L≥64575，某个核发生进位）`或者 `-1（L<≤960，某个核发生借位）`。

:::tip 进位，借位表
## 完整的进位表

| 进位模式 | L 范围 | 进位方向 | B 的变化 | 哪些方向进位 |
|---------|--------|--------|---------|-----------|
| `{}` 安全 | 961-64574 | 无 | B → B | 无 |
| `{+Z}` | 64575-65504 | 向上 | B → B+1 | +Z |
| `{+Z,+Y}` | 65505-65534 | 向上 | B → B+1 | +Z, +Y |
| `{+Z,+Y,+X}` | 65535 | 向上 | B → B+1 | +Z, +Y, +X |
| `{-Z}` | 1-960 | 向下 | B → B-1 | -Z |
| `{-Z,-Y}` | 1-30 | 向下 | B → B-1 | -Z, -Y |
| `{-Z,-Y,-X}` | 0 | 向下 | B → B-1 | -Z, -Y, -X |

:::

此时，比如单`{+Z}`进位时，bucketIndex 分组会变成这样：
```
u = A ^ B
v = (A+1) ^ B 
w = (A-1) ^ B
z = (A+1) ^ (B+1) //+Z在这里
```
`{+Z,+Y}` 时这样：
```
u = A ^ B
v = (A+1) ^ B 
w = (A-1) ^ B
y = (A-1) ^ (B+1) //+Y在这里
z = (A+1) ^ (B+1) //+Z在这里
```
`{+Z,+Y,+X}` 时这样：
```
u = A ^ B
v = (A+1) ^ B 
w = (A-1) ^ B
y = (A-1) ^ (B+1) //+Y在这里
xz = (A+1) ^ (B+1) //+Z,+Z　在这里
```
但由于 bucketIndex 可能在计算方式不同的情况下结果相同，为了最保险的结论。
我们可以对它们的组合进行穷举（比如对+Z+Y进行穷举）：

```java
Set<String> uniqueOrders = new HashSet<>();

for (int A = 0; A < 16; A++) {
    for (int B = 0; B < 16; B++) { // A是4位，B是4位，总共16*16个组合
        // 在 {+Z,+Y} 模式下，计算 5 个桶值
        int u = A ^ B;
        int v = ((A+1) & 15) ^ B;
        int w = ((A-1) & 15) ^ B;
        int y = ((A-1) & 15) ^ ((B+1) & 15);
        int z = ((A+1) & 15) ^ ((B+1) & 15);
        
        // 7 个元素及其桶值
        int[] elements = {0,     1,     2,     3,     4,     5,     6};
        String[] names = {"自身", "-Y",  "+Y",  "-Z",  "+Z",  "-X",  "+X"};
        int[] buckets  = {u,     v,     y,     w,     z,     w,     v};
        
        String order = stableSortByBucket(names, buckets);
        uniqueOrders.add(order);
    }
}

System.out.println(uniqueOrders.size());  // 输出：14
uniqueOrders.forEach(System.out::println);
```
最终得到以下结果：

| 进位模式 | 该模式下产生的不同顺序 | 3%失效区中的占比 |
|---------|----------------------|------|
| `{+Z}` 进位 | 12 | 1.42% |
| `{+Z,+Y}` 进位 | 14 | 0.05% |
| `{+Z,+Y,+X}` 进位 | 6 | 0.0015% |
| `{-Z}` 进位 | 12 | 1.42% |
| `{-Z,-Y}` 进位 | 14 | 0.05% |
| `{-Z,-Y,-X}` 进位 | 6 | 0.0015% |

那么，
`2x（12+14+6）+6=70`？下结论前再等等，
