# 风格规范

这份规范是从 `docs/posts/` 里的文章归纳出来的。引号里的句子都是原文。目标是「像博主写的」，而不是「像一篇规范的技术文档」：博主的文章是一个人带着读者一起查问题，有疑问、有发现、有转折。

## 目录

1. 人称和对读者的称呼
2. 口语化程度

## 1. 人称和对读者的称呼

- 主体人称是「**我们**」：既指作者，也把读者拉进来一起分析。
  - 「仔细寻找后，我们可以发现……」
  - 「一篇漏洞报告引起了我们的注意。」
  - 「我们继续追踪源码，看看 `onGround` 究竟是如何被设置的。」
- 「**我**」只在讲亲身经历时出现：
  - 「当我第一次听到这个说法时，我先是震惊，随即又觉得不可置信——真的会有这么庞大的计算量吗？」
  - 「我和几位群友在讨论时，被告知“未对齐的TNT簇”会造成极大的卡顿。」
  - 自创译名时：「移动解释权（Authority，至少我倾向于这样描述）」
- 称读者为「**你**」，常直接提问或预判读者的反应：
  - 「你真的了解比较器更新吗？」「你是不是也这样认为呢？」
  - 「如果你足够敏感，“掉落物”，“4GT”会让你想到一个机制。」
  - 「现在，你大概能猜到我们将要说什么了，没错。」
  - 「现在，你可能感到困惑：」后面接一个引用块，替读者把疑问说出来。

## 2. 口语化程度

主体是**清楚、偏书面的技术叙述**，句子不长，一段讲一件事。中间点缀少量口语和轻吐槽，让读者喘口气。每篇用一两处就够，不要每段都俏皮。

- 「别害怕，下面有文字版的伪代码：」（在一大段源码后面）
- 「~~“活塞不提供y轴动量”已经说了n次了哈哈~~」（删除线吐槽）
- 「那...对于上述的情况，我们应该怎么办呢..?」
- 「（其实指**实心方块**，Mojang 的命名在这里略显误导）」

## 3. 过渡句和口头禅

推导是一步一步走的，每一步之间用这些句子衔接。选用最贴合当下的，不要堆砌。

| 用途 | 常用句式 |
|---|---|
| 抛出疑问 | 「但事情还没结束。」「但是——事情真的有这么简单吗？」「问题在于，这是什么导致的呢？」「那……又是哪来的呢？」「那么先前的说法是真的吗？若是真的，为何……？」 |
| 进入下一层 | 「我们继续深入...」「让我们继续深入。」「我们继续追踪源码，看看……」「那么，让我们再来看看 `xxx`。」「让我们看看第一条，」「再看看第三条：」 |
| 观察 | 「仔细观察，……」「仔细对比，我们就能发现问题：」「可以看到，……」「看到了吗？」「在这里，我们可以看到……」 |
| 推断 | 「综合这些信息，我们大致可以推断出原因：」「有了上述推断后，我们可以以……为切入点」「这意味着，……」 |
| 阶段结论 | 「现在，我们对……就一目了然了：」「我们现在可以证实，……」「现在，我们终于可以更清晰地理解……」「由此可见，问题的本质是：」「至此，……」 |
| 换个说法 | 「换句话说，」「也就是说，」「简而言之，」「可以这样总结：」 |
| 谨慎 | 「但下结论前还得再等等，……」「为了最保险的结论，我们可以……」 |
| 强调反常 | 「这是有趣的」「令人意外的是，」「奇怪的是，」「这才是……真正有趣的地方。」 |
| 引出实际应用 | 「这一发现也带来了一个更加激进的优化思路。」「值得庆幸的是，……将会帮你解决这个烦恼。」 |

「乍听之下 / 实际上」是博主很喜欢的对照结构：

> 这句话乍听之下，似乎是在说：……
> 但实际上，Minecraft 的实现方式是：……

## 4. 对不确定内容的语气

博主不会把没把握的事写死。草稿里同样用这些说法，并配合 `::: warning 待验证` 容器（格式见 markdown-format.md）。

- 「至于原作者为何采用……，我们不得而知，也许是出于对类似问题的担忧。」
- 「`this.isLocalInstanceAuthoritative()`，待考察，先假设通过吧。」
- 「令人遗憾的是，这篇文章并无法为你揭示QC的确切来源。」
- 「理论上这种情况也会在……时发生」
- 「在原版 Minecraft 中，似乎只有潜影盒会触发此问题。」

结论被验证过时，要说清楚怎么验证的：「通过 **1.21.1** 的 Fabric Mod 开发环境，进行断点调试，我们验证了上述猜想。」「[这个视频](…)验证了这个理论。」

## 5. 术语习惯

- **社区缩写直接用，不额外解释**：NC 更新、PP 更新、QC、CUD、0t、gt / GT（游戏刻）、b36、EMP、更新核、一阶 / 二阶更新核、计划刻、方块事件、区块刻、假方块、幽灵方块。
- **中文术语首次出现时在括号里注英文或代码名**：「计划刻（scheduled tick）」「桶号（bucket index）」「方块事件（Block Event）」「BlockState（方块状态）」。
- **自己起的译名要说明**：「移动解释权（Authority，至少我倾向于这样描述）」。
- **版本号写全、写准**：`1.21.4`、`24w45a`、`25w02a`、`26.2`、`beta1.2_02`。涉及版本差异时一定写明起止版本，并在 frontmatter / TL;DR 里体现。
- **会指出官方命名不准确的地方**，帮读者避免误解（如 `isRedstoneConductor` 实际判断的是实心方块）。
- **点名并链接相关的人和来源**：「感谢 Chem 提供的帮助」「自 **Tjs-Redstone** 的优化版」「引用FallenBreath的简化阶段树」。人名和链接只能来自素材。

## 6. 类名、方法名和映射

- 所有类名、方法名、字段名、变量名都用行内代码：「`onGround` 变量，在第一次攀爬完成后便由 `true` 变为了 `false`」。
- 方法第一次出现时可以带签名：「`Entity.java` 中，`Vec3 collide(final Vec3 movement)` 方法」。
- **映射名跟着素材走**：
  - 默认用 Mojang 映射（近期文章都是：`LevelTicks`、`RedstoneWireBlock`、`isRedstoneConductor`、`isLocalInstanceAuthoritative`）。
  - 素材是 Yarn（`Vec3d`、`World`、`method_xxxxx`、`adjustMovementForCollisions`）时就用 Yarn，并在文中说一句用的是哪套映射。
  - 两套名字都在素材里时，像这样同时给出：「实现比较器更新的方法在 Yarn 映射中叫 `world.updateComparators`，而在 Mojang 映射中则叫 `level.updateNeighbourForOutputSignal`」。
  - **不要凭记忆把一套映射翻译成另一套**；需要对照名而素材没有时，放进待验证容器。
- 古老版本直接引用反编译名（`func_31041_f`、`var1.q`），并说明源码从哪来。

## 7. 要避免的写法

- 不模仿原文的笔误、错别字、繁体字（如「我們」「计划科」「跨区快」）和全角破折号日期。
- 不用 emoji，不用「🚀」「✅」这类装饰。
- 不写空泛的总结套话：「总而言之，理解这一机制至关重要」「希望本文对你有所帮助」「让我们一起探索……的奥秘」。博主的结尾都有具体内容：结论、应用、收获，或一个具体的练习。
- 不用过度正式的公文腔：「本文旨在」「综上所述」「值得注意的是」可以偶尔用，但别成串出现。
- 不要把每一节都写成整齐的「定义 → 原理 → 总结」模板。博主的推导是跟着问题走的：一个发现引出下一个疑问。
- 不要过度使用粗体和 `==标记==`。一段里最多一两处真正的重点。
