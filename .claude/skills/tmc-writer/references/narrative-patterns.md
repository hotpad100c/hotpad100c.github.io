## 1. 四种文章类型

先判断素材属于哪一类，再按对应骨架列大纲。骨架是常见顺序，不是硬模板，素材不支持的节可以省略。

### A. 纠正误解

代表：`QC之源：一个广为流传的误解.md`、`关于比较器更新.md`、`重新认识方块更新.md`

适用：社区流传的说法、wiki 描述、常见教程里的简化说法有误或容易误导。

骨架：
1. **引用那句流行说法**（引用块，常加 `==…=={.important}`），说明它有多普遍：「不知道从什么时候开始，大多数Minecraft玩家心中都埋下了这样的印象。」
2. **把读者拉进来**：「你是不是也这样认为呢？」「但是——事情真的有这么简单吗？」
3. **给出反证或原始依据**：wiki 的另一段原文、加入时间线、反编译源码。
4. **逐步拆解真实机制**（源码 + 逐行解释）。
5. **定义式结论**（引用块），直接回应开头那句说法：「那个“活塞抄了门”的解释，是错误的。」
6. 收尾：如果真相仍然未知，诚实说明；可以有一句启发式结尾。

标题可以用编号：`## 01｜误解`、`## 02｜时间线`、`## 03｜所以？`；或用问句：`# 你真的了解比较器更新吗？`、`# 所以，它是什么？`。

### B. 现象 / 装置解析

代表：`光速电梯的完全解析.md`、`红石粉连接异常.md`、`实体移动碰撞过程.md`、`1.21.5+的掉落物与岩浆.md`

适用：一个具体现象、一台装置、一个反常行为，需要从源码上解释为什么。

骨架：
1. （结论明确时）**TL;DR / 一句话概括根因**，放在最前面。
2. **现象**：图或视频链接 +「如上图所示，……」，指出「看起来」和「实际」的矛盾；提到原作者或视频时附链接。
3. **列出本文要回答的问题**（问题清单，可以带子问题「误区：……」）。
4. **每个问题一个 `#` 大节**，标题就是那个问题本身。每节内部：
   - 先推测（「综合这些信息，我们大致可以推断出原因」）；
   - 再找源码验证，顺着调用链往下读；
   - 必要时用排除法，把条件逐条列出来判断真假；
   - 给出这一节的小结论。
5. **对应的优化 / 应用**：基于结论能做什么（`## 对应的优化：`）。
6. **收获**：顺带发现的机制（`## 收获：`）。
7. **版本差异**（如适用）：对比不同版本源码，用 `// [!code --]` / `// [!code ++]` 标出改动，给出可用版本范围。
8. **总结**：引用块或 bullet，把根因完整串一遍。

### C. Bug 报告解析

代表：`MC-310372解析.md`

适用：解释一篇 Mojira 漏洞报告。

骨架：
1. 标题里带编号和一句话描述：`# MC-310372 (0gt 延迟调度引发的区块刻乱序问题)`
2. 「一篇[漏洞报告](链接)引起了我们的注意。」+ 报告翻译（引用块；截掉的部分用 `...` 标明）。
3. 「初看报告里的描述，仍然云里雾里」，说明本文要帮读者理解什么。
4. 编号小节：`## 1. xxx 的逻辑分析` → `## 2. 报告中的具体情况分析` → `## 3. 总结` → `## 4. 实际案例` → `## 5. 附加`。
5. 总结常用「起因 / 经过 / 结果 / 表现」结构。
6. 实际案例：按游戏刻编号列出步骤（「第0gt，……」「第11gt，……」），并链接验证视频。
7. 附加：「理论上……」的延伸，配待验证容器。

### D. 数学推导 / 机制教程

代表：`红石粉更新的数学规律.md`（数学推导）、`仅客户端的方块操纵.md`（机制教程）

**数学推导**骨架：
1. `# TL;DR`：几条带具体数字的结论（概率、组合数、范围）。
2. `# 前言`：大家原来怎么认为 → 实际上有规律可循；工具或模拟器放在 `::: tip`。
3. 先讲基础数据结构 / 公式（用比喻，例如「想象有一组固定数量的抽屉」）。
4. `## 规律1`、`## 规律2`……每条规律：先用引用块写出规律本身，再「为何会这样呢？」推导。
5. 推导中穿插：公式、二进制、表格、可视化图（图后写图例说明）、穷举代码（长的放进 `<details>`）。
6. 「但下结论前还得再等等」：考虑例外和重复情况。
7. `## 总结`：bullet 列出每条可用的结论。

**机制教程**骨架：
1. `## 何为……`：从读者听说过的用法讲起，说明「它的能耐远不止如此」。
2. 讲清原理的前提（例如服务端 / 客户端同步、游戏刻阶段顺序）。
3. 用小标题提问推进：`### 但真正的问题是：如何制造这种不同步？`
4. 每个用法：`::: demo-wrapper` 里放装置图 + 操作步骤 + 服务端 / 客户端分别看到什么。
5. 阶段性总结用 `> ### 一句话原理`。
6. 结尾留一个具体练习：「不妨试试看用假活塞头，做出一个“六头活塞”吧。」

## 2. 通用的推导手法

- **先猜后验**：先从现象推出可能原因，再去源码里找证据，最后找到能「验证」的那段代码或实测。不要一上来就把答案摊开，除了 TL;DR。
- **顺着调用链读**：每读一层源码，说出「这一层做了什么，还缺什么」，然后「我们继续深入」。
- **排除法**：进入某段逻辑需要几个条件时，把条件列成引用块或列表，逐条标真假，剩下可疑的那条就是关键。
- **对照**：常识说法 vs 真实实现（「乍听之下 / 但实际上」）；两处相似代码并排对比找差异（红石粉连接异常里的「第一段代码 / 第三段代码」）。
- **穷举或调试**：结论涉及「只有几种可能」「概率」时，用代码穷举；涉及运行时状态时，提到断点调试。只能写素材里真的做过的验证。
- **回扣**：后面的结论要回扣前面的问题清单或误解（「结合前文“……”的结论，我们可以重新分析这一说法」）。

## 3. 源码、图、表、伪代码各放在哪

- **源码**：每个推导步骤先贴源码，紧接着解释。解释的三种方式：
  - 逐行 bullet：「* `for (Direction direction : …)` 表示只遍历水平四个方向」；
  - 伪代码：源码复杂时，「别害怕，下面有文字版的伪代码：」，用 ```text 写；
  - 一句话概括：「简而言之，当……时，游戏会……」。
- **源码之前**一般有一句说明它在哪：「它是位于`Entity.class`的`move(...)`」「在`RedstoneWireBlock.java`中搜索，可以找到5处调用」。
- **图**：现象描述处放一张；文字难懂时「文字太多还是难以理解。下图为……」，图后用列表写图例。
- **表**：枚举条件、概率、版本对照、进位借位等。
- **长代码 / 穷举程序**：放进 `<details><summary>穷举代码</summary> … </details>`。

## 4. 结论和收尾

- 定义式结论用引用块：「> **比较器更新** 是一种向某个方块相邻，或相邻的实心方块后方的比较器发送 NC 更新的特殊更新机制。」
- 长文以 `# 总结` 结束，用引用块写一段完整的因果链，或用 bullet 逐条列出结论。
- 可以附 `## 收获`、`## 附加`、`## 对应的优化`，内容都是具体的。
- 真相仍未知时，诚实地说出来，并说明「至少我们已经知道」什么。
