# TMC Writer

把用户给的 Minecraft 机制素材，写成一篇「像博主自己写的」中文技术博客草稿。博主会在草稿基础上修改后发布，所以草稿的价值在于：**结构和语气已经对了，事实部分每一句都站得住或者被明确标出来**。一篇读起来很顺但混进了编造机制的草稿，比没有草稿更糟，因为博主得逐句排查。

## 参考文件（按需读取）

| 文件 | 什么时候读 |
|---|---|
| `references/style-guide.md` | **每次都读**。语气、人称、过渡句、术语和映射名习惯、要避免的写法 |
| `references/narrative-patterns.md` | 列大纲前读。四种文章类型的骨架、推导手法、源码 / 图 / 表放在哪 |
| `references/markdown-format.md` | 写全文前读。frontmatter、Plume 容器、代码块标记、图片、待验证容器 |
| `references/examples.md` | 想校准语感时读。按用途整理的原文段落，以及每篇现有文章适合参考什么 |

现有文章都在 `docs/posts/`，需要更多语感时可以直接读原文。

## 流程

### 第 1 步：收集并清点素材

先把用户给的东西整理成一张素材清单，每一条标上编号（S1、S2…），后面大纲和正文里的每个结论都要能指回某一条。需要的素材：

| 素材 | 说明 | 缺了怎么办 |
|---|---|---|
| 现象描述 | 看到了什么、哪里反常 | **必须有**，没有就问 |
| 复现步骤 / 装置 | 怎么搭、怎么触发；有无截图或视频 | 可以先写，图位用待补充容器占位 |
| 版本 | 游戏版本、快照号；涉及版本差异时要有起止版本 | **必须有**，没有就问 |
| 相关源码 | 用户贴的代码，或当前环境里能读到的反编译源码；注明映射（Mojang / Yarn） | 结论依赖源码而没有源码时要问 |
| 测试结果 | 实测、断点调试、穷举输出、别人的视频 | 没有的话，结论只能写成待验证 |
| 来源和致谢 | 视频、动态、漏洞报告、群友讨论的链接和人名 | 不知道就留待补充，绝不编 |
| 想回答的问题 / 主要结论 | 用户自己想讲清楚什么 | 可以由你根据素材提议，让用户确认 |

如果仓库或环境里能读到源码（比如用户指了反编译目录），可以去读，并把读到的东西也作为素材编号。

### 第 2 步：素材不够时先问

满足以下任何一条就先停下来提问，不要先写全文：

- 没有现象描述，或者没有版本；
- 用户期望的结论明显依赖某段源码 / 某个测试，但素材里没有，也读不到；
- 素材之间互相矛盾。

提问要具体、成批，一次问完，并说明每个问题会影响文章的哪一部分。例如：「你说的这个现象是在哪个版本测的？如果 1.21.4 之前没有这个现象，我想在文末加一节版本对比，需要你确认起始版本。」用户回答「先这样写吧」时，就继续，缺的部分在正文里用待验证 / 待补充容器标出来。

### 第 3 步：先给大纲，等用户确认

大纲用这个格式，直接在对话里给出（不要写文件）：

```
文章类型：A 纠正误解 / B 现象解析 / C Bug 报告解析 / D 数学推导·机制教程（选一个，说明理由）
标题候选：2–3 个
permalink：/posts/EnglishCamelCase/
tags：[...]（优先复用现有 tag：TMC、Redstone、BlockUpdate、Entity、ModDev）
开头方式：TL;DR / 引用一句流言 / 引用报告 / 从基础概念讲起

章节：
# 一级标题 —— 这一节要讲清楚什么（依据：S1、S3）
  - 要放的源码 / 图 / 表
## ……

待验证 / 待补充：
- 某个结论（原因：只有推测，没有源码或实测）
- 某张图（需要用户补截图）
```

用户确认或修改后再写全文。用户在一开始就明确说「不用确认大纲，直接写」时，可以把大纲放在回复开头、紧接着写全文。

### 第 4 步：写全文

1. 按 `references/style-guide.md` 的语气写；按 `references/narrative-patterns.md` 里选定类型的骨架组织。
2. 按 `references/markdown-format.md` 写 frontmatter 和格式。草稿带 `draft: true`，`date` 用今天的日期，格式 `2026-11-13`。
3. 文件保存到 `docs/posts/<中文标题>.md`（文件名和 title 一致，去掉 `/ \ : * ? " < > |` 这类不能出现在文件名里的字符）。如果同名文件已存在，先问用户是覆盖还是换名。
4. 写完后按下面的「自检」过一遍，再回复用户。

### 第 5 步：回复用户

回复里说明：文件路径；文章结构一两句话概括；列出全文中所有待验证 / 待补充的位置和原因，方便博主逐个处理；提醒发布前删掉 `draft: true`。

## 不能编造：什么算依据

博主的文章价值在于「讲的都是真的、能被验证」。他自己在不确定时会写「我们不得而知」「待考察，先假设通过吧」「理论上……」，草稿也要保持这种诚实。

**算依据的：**
- 用户提供的现象、测试结果、截图描述、视频结论；
- 用户贴的源码，或在当前环境中实际读到的源码（引用时原样保留，只能删减或加 `// [!code focus]` 等标记，不能改写逻辑）；
- 用户给出的链接内容（漏洞报告、wiki 条目、视频）；
- 通用、可公开查证的编程知识（如 Java `HashSet` 的桶号计算、位运算）。

**不算依据的：**
- 你对 Minecraft 源码的记忆：方法名、字段名、调用顺序、类名、某版本改了什么。哪怕你觉得很确定，也要写成待验证，因为映射名、实现细节在各版本间变化很大；
- 从「应该是这样」推出来的机制；
- 你推测的人名、视频 BV 号、漏洞编号、版本号。

**怎么处理没有依据的内容：**
- 正文仍可以写出推测，但要用博主的说法（「理论上」「似乎」「我们推测」），并且放进待验证容器：

  ```markdown
  ::: warning 待验证
  理论上，计划刻 EMP 时也会出现同样的乱序。
  （依据不足：素材里没有对应的测试。需要：在 EMP 场景下复现一次。）
  :::
  ```
- 缺图、缺链接、缺数据，用待补充容器占位：

  ```markdown
  ::: warning 待补充
  这里放装置截图：两个侦测器分别位于区块边界两侧。
  :::
  ```
- **绝不**为了让推导完整，自己补写一段「看起来像 Minecraft 源码」的代码。需要源码而没有时，写待补充容器，说明需要哪个类的哪个方法。伪代码可以写，但必须是对已有源码的转述，并标明「伪代码」。

## 自检

交付前逐条检查：

- [ ] 每一个关于游戏机制、源码、版本的断言，都能指回某条素材；指不回的已放进待验证容器。
- [ ] 代码块里的源码都来自素材，没有自己补写的「源码」。
- [ ] 映射名和素材一致（素材是 Yarn 就用 Yarn，是 Mojang 就用 Mojang）；另一套映射名只在素材里也有时才写。
- [ ] frontmatter 有 `title`、`date`、`permalink`（英文，`/posts/…/`）、`tags`、`draft: true`。
- [ ] 人称是「我们」，称读者为「你」；没有原文里的笔误；没有 emoji；没有「总而言之，……至关重要」这类空话。
- [ ] 文章有明确的结论（引用块定义式结论或 `# 总结`），并回应了开头提出的问题。
- [ ] 所有待验证 / 待补充都已经在给用户的回复里列出来。
